# Vanilla JSX

A small single-page application built with **JSX and vanilla JavaScript** — no React, no UI framework, and no runtime dependencies.

Vite is used for the dev server, production build, and the JSX transform. Everything else (the JSX factory, virtual DOM diff, state store, and router) is implemented in this repository in a handful of small modules.

The app includes four pages:

- **Home** — an overview of the demo
- **Counter** — interactive state updates
- **Todos** — keyed list rendering with add, toggle, filter, and remove
- **How it works** — a walkthrough of the implementation

It also supports a persistent light/dark theme and hash-based routing.

## Why this exists

Most JSX projects assume React. This project shows that JSX is ultimately just syntax that compiles to function calls. By configuring Vite's Oxc transform to use a classic JSX runtime, every JSX element compiles to a call to our own `h()` function:

```jsx
<button class="primary" onClick={save}>Save</button>
```

becomes:

```js
h('button', { class: 'primary', onClick: save }, 'Save')
```

The result is a tiny, understandable implementation of the ideas that frameworks build on:

- a virtual node representation
- a keyed DOM reconciliation algorithm
- one-way data flow through a store
- declarative event and attribute updates
- client-side routing

It is intended as a learning demo, not a production framework.

## Features

- JSX compiled to plain function calls by Vite/Oxc
- Hand-written `h()` virtual node factory
- Keyed virtual DOM diffing and patching
- In-place text, attribute, style, and event updates
- Controlled inputs that keep focus and cursor position
- Centralized store with `getState`, `setState`, and `subscribe`
- Hash router with no server configuration
- Persistent light/dark theme using `localStorage`
- Responsive layout with accessible navigation and controls
- Zero runtime dependencies

## How it works

The entire data flow is intentionally short:

```text
User event
  -> action
  -> store.setState(...)
  -> subscribers run
  -> draw() renders <App />
  -> render() patches the previous virtual tree into the DOM
```

### 1. JSX is configured as a classic runtime

Vite 8 uses Oxc to transform JSX. The configuration in `vite.config.js` does two related things:

```js
import { defineConfig } from 'vite'

const jsx = {
  runtime: 'classic',
  pragma: 'h',
  pragmaFrag: 'Fragment',
}

export default defineConfig({
  oxc: {
    jsx,
  },
  optimizeDeps: {
    rolldownOptions: {
      transform: {
        jsx,
      },
    },
  },
})
```

- `oxc.jsx` configures the transform used for application modules.
- `optimizeDeps.rolldownOptions.transform.jsx` configures the transform used by Vite's dev-time dependency scanner.

The second block is required. Without it, the dependency scanner falls back to the automatic runtime, tries to import `react/jsx-dev-runtime`, and prints:

```text
Failed to run dependency scan ... react/jsx-dev-runtime ... could not be resolved
```

Because the runtime is `classic`, each `.jsx` file imports `h` explicitly:

```jsx
import { h } from '../jsx.js'
```

If you use fragments in a file, import `Fragment` too:

```jsx
import { h, Fragment } from '../jsx.js'
```

### 2. The JSX factory

`src/jsx.js` turns JSX arguments into a plain virtual node object:

```js
export function h(type, props, ...children) {
  const { key = null, children: nested, ...rest } = props || {}
  const nodes = children.length ? children : nested == null ? [] : [nested]

  return {
    type,
    key,
    props: rest,
    children: nodes.flat(Infinity).filter(isRenderable),
  }
}
```

For example:

```js
h('button', { class: 'primary', onClick: save }, 'Save')

// {
//   type: 'button',
//   key: null,
//   props: { class: 'primary', onClick: save },
//   children: ['Save']
// }
```

The `type` can be:

- a tag name such as `'div'` or `'button'`
- a function component such as `Counter`
- the `Fragment` symbol
- `'#text'` for normalized text nodes

### 3. Mounting and patching

`src/render.js` contains two main operations:

- `mount()` creates DOM nodes for a virtual node.
- `patch()` compares an old virtual node with a new one and updates the DOM.

`render(vnode, container)` starts the process and stores the current virtual tree on the container:

```js
export function render(vnode, container) {
  container._vnode = patch(container, container._vnode || null, vnode, null)
}
```

During a patch:

- **Text nodes** are updated by comparing `nodeValue`.
- **Elements of the same type** are reused, their props are updated, and their children are patched.
- **Different element types** are replaced.
- **Function components** are invoked to produce a virtual subtree, which is patched recursively.
- **Keyed children** are matched by `key` and moved into the correct order.
- **Unkeyed children** are matched by position.
- **Removed children** are detached from the DOM.

The children algorithm returns the patched child list so the stored virtual tree always points at the DOM nodes that actually exist.

Placement is handled by `place()`, which avoids moving nodes that are already in position and ignores anchors that were detached during a replacement. This prevents `insertBefore` errors when one page replaces another.

### 4. Props, styles, and events

Props are applied by `updateProps()`, `setProp()`, and `removeProp()`.

- `onClick`, `onInput`, `onChange`, and other `onX` props become event listeners.
- `className` is mapped to `class`.
- `style` accepts a string or an object. Object keys use CSSStyleDeclaration naming (`backgroundColor`) and custom properties start with `--`.
- `value` and `checked` are set as DOM properties so controlled inputs behave correctly.
- Boolean attributes such as `disabled` and `hidden` are added or removed.
- Other values are written with `setAttribute`.

Because the virtual DOM is patched in place, a controlled input keeps its focus and cursor when its value is updated from the store.

### 5. State

`src/store.js` is a tiny observable store:

```js
const store = createStore({ count: 0 })

const unsubscribe = store.subscribe((state) => {
  console.log(state)
})

store.setState({ count: 1 })
store.setState((state) => ({ count: state.count + 1 }))
```

`setState()` accepts either a partial object or an updater function. Subscribers run synchronously after the state changes.

All application state lives in the store created in `src/main.jsx`:

```js
const store = createStore({
  route: getRoute(),
  theme: preferredTheme(),
  count: 0,
  step: 1,
  draft: '',
  filter: 'all',
  todos: [/* ... */],
})
```

Actions are plain functions that call `store.setState()`:

```js
const actions = {
  increment() {
    store.setState((state) => ({
      ...state,
      count: state.count + state.step,
    }))
  },

  addTodo() {
    const text = store.getState().draft.trim()
    if (!text) return

    store.setState((state) => ({
      ...state,
      draft: '',
      todos: [...state.todos, { id: nextTodoId++, text, done: false }],
    }))
  },
}
```

A single subscriber re-renders the app:

```js
function draw() {
  const state = store.getState()
  document.documentElement.dataset.theme = state.theme
  render(<App state={state} actions={actions} />, root)
}

store.subscribe(draw)
draw()
```

Every store change re-runs the component functions and diffs the result against the previous virtual tree. The render functions are cheap; the patcher limits actual DOM work to the nodes that changed.

### 6. Routing

`src/router.js` uses the URL hash, so no server rewrite rules are needed:

```js
export function getRoute() {
  const hash = window.location.hash.replace(/^#/, '')
  return hash.startsWith('/') ? hash : '/'
}

export function onRouteChange(handler) {
  window.addEventListener('hashchange', () => handler(getRoute()))
}
```

`main.jsx` stores the current route in the store:

```js
onRouteChange((route) => {
  store.setState({ route })
  window.scrollTo(0, 0)
})
```

`App.jsx` maps routes to page components:

```js
const routes = {
  '/': Home,
  '/counter': Counter,
  '/todos': Todos,
  '/about': About,
}
```

Links are ordinary anchors:

```jsx
<a href="#/todos">Todos</a>
```

The `hashchange` event updates the route, which triggers a render, which replaces the page component.

## Adding a page

1. Create a component in `src/pages/`:

   ```jsx
   // src/pages/Settings.jsx
   import { h } from '../jsx.js'

   export function Settings({ state, actions }) {
     return (
       <section class="page">
         <p class="eyebrow">Settings</p>
         <h1>Settings</h1>
         <p class="lede">The current theme is {state.theme}.</p>
         <button class="button primary" type="button" onClick={actions.toggleTheme}>
           Toggle theme
         </button>
       </section>
     )
   }
   ```

2. Register it in `src/App.jsx`:

   ```jsx
   import { Settings } from './pages/Settings.jsx'

   const routes = {
     '/': Home,
     '/counter': Counter,
     '/todos': Todos,
     '/about': About,
     '/settings': Settings,
   }
   ```

3. Add a navigation link in `src/components/Header.jsx`:

   ```js
   const links = [
     { path: '/', label: 'Home' },
     { path: '/counter', label: 'Counter' },
     { path: '/todos', label: 'Todos' },
     { path: '/settings', label: 'Settings' },
     { path: '/about', label: 'How it works' },
   ]
   ```

## Adding state and actions

Add the initial value to the store in `src/main.jsx`:

```js
const store = createStore({
  // ...
  notifications: true,
})
```

Add an action:

```js
const actions = {
  // ...
  toggleNotifications() {
    store.setState((state) => ({
      ...state,
      notifications: !state.notifications,
    }))
  },
}
```

Use it from a component:

```jsx
<button
  class="button"
  type="button"
  onClick={actions.toggleNotifications}
>
  Notifications: {state.notifications ? 'on' : 'off'}
</button>
```

Pass `state` and `actions` to any component that needs them. There is no context or hooks layer.

## Styling

`src/style.css` defines the visual system with CSS custom properties.

Light and dark themes are selected with a data attribute on the root element:

```css
:root {
  --bg: #f6f6fb;
  --text: #191924;
  --accent: #6355f5;
}

:root[data-theme='dark'] {
  --bg: #0d0d14;
  --text: #f2f2f7;
  --accent: #8b7dff;
}
```

`index.html` sets the theme before the app loads to avoid a flash of the wrong theme, and `main.jsx` keeps it in sync with the store and `localStorage`.

The layout is responsive, with a mobile breakpoint at `760px`. Focus-visible outlines and reduced-motion preferences are respected.

## Design decisions

### No hooks or component-local state

State lives in one store. Components are pure functions of `state` and `actions`. This keeps the implementation small and makes the data flow easy to follow.

### Full re-render, minimal DOM updates

Every store change invokes the component tree again. The virtual DOM diff ensures that only changed text, props, and nodes are touched in the document. For a demo of this size, the cost is negligible.

### Explicit `h` imports

Instead of injecting the JSX factory into every file, each JSX module imports `h` explicitly. This makes dependencies visible and avoids injecting imports into the runtime module itself.

Because the JSX is compiled to `h(...)` calls before the app runs, the import is required even though `h` never appears literally inside JSX in the source. Editors that do not read `vite.config.js` may report the import as unused. `jsconfig.json` teaches VS Code's TypeScript/JavaScript language service about the classic factory:

```json
{
  "compilerOptions": {
    "allowJs": true,
    "checkJs": false,
    "jsx": "react",
    "jsxFactory": "h",
    "jsxFragmentFactory": "Fragment"
  },
  "include": ["src"]
}
```

The file is editor metadata only; Vite and the build are unaffected by it.

### Hash routing

Hash routing requires no server configuration and works when the built `dist/` directory is served from any static host or subpath.

### Keyed lists

Lists that can reorder or change (todos, features, filters, navigation links) use stable keys. This lets the patcher preserve DOM nodes and component state, such as checkbox state and input focus.

## Limitations

This is a learning demo, not a complete framework. In particular:

- No hooks, context, suspense, portals, or error boundaries
- No server-side rendering or hydration
- No async components
- `Fragment` renders a `div` with `display: contents` rather than a true fragment
- No SVG namespace handling; inline SVG created through JSX would need renderer changes
- Unkeyed children are matched by position, which can cause surprising reuse when lists reorder
- Every store change re-runs the full component tree
- Event listeners are reattached whenever an inline handler's function identity changes
- Routing is hash-only; there is no history API integration
- No TypeScript types or test suite in the repository

For a production app, use a framework or add the missing pieces deliberately.

## Troubleshooting

### `react/jsx-dev-runtime` could not be resolved

This means the dev-time dependency scanner is using the automatic JSX runtime. Make sure `vite.config.js` configures JSX in **both** places:

```js
export default defineConfig({
  oxc: {
    jsx: { runtime: 'classic', pragma: 'h', pragmaFrag: 'Fragment' },
  },
  optimizeDeps: {
    rolldownOptions: {
      transform: {
        jsx: { runtime: 'classic', pragma: 'h', pragmaFrag: 'Fragment' },
      },
    },
  },
})
```

Then clear the Vite cache and restart:

```bash
rm -rf node_modules/.vite
npm run dev
```

### A page appears twice or `insertBefore` fails

The patcher must never use a removed node as an insertion anchor. `place()` in `src/render.js` guards against this. If you change the patcher, keep that guard and make sure patched child lists are stored back on the virtual node.

### The theme does not persist

Theme persistence uses `localStorage` under the key `vanilla-jsx-theme`. Private browsing modes or browser settings that block storage will fall back to the system preference for the session.
